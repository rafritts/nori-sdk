# SPEC-08 — Incident Response Exercise

## Purpose

This is not a demo. It is a structured stress test of Nori's multi-agent
architecture under realistic conditions: parallel investigation, deep iteration
loops, sub-agent spawning, HITL at a genuine decision point, and multi-file
remediation followed by automated verification.

Target spend: ~$0.50 at grok-4.3 rates.

---

## Directory Layout

```
exercises/
└── incident_response/
    ├── run.py                  # entry point: python exercises/incident_response/run.py
    ├── setup.py                # generates the broken service fixture
    └── service/                # the "broken" service (generated by setup.py)
        ├── app.py              # FastAPI-style handlers with planted bugs
        ├── db.py               # database layer — missing index, leaked connections
        ├── cache.py            # cache layer — stale TTL bug
        ├── schema.sql          # table definitions (no index on orders.customer_id)
        ├── seed.sql            # seed data (10k rows, enough to make scans slow)
        ├── git_log.md          # fake recent commit history (narrative, not real git)
        ├── logs/
        │   ├── app.log         # mixed real errors + red herrings from "auth-service"
        │   └── slow_queries.log
        └── tests/
            ├── test_api.py     # pytest suite — starts failing after the bugs land
            └── conftest.py
```

`setup.py` is idempotent. Running `run.py` calls it automatically before
starting any agents. The generated fixture is committed (or reproducible) so
the exercise is deterministic.

## Planted Bugs

Four bugs are planted in the service. They are causally linked:

| # | Bug | Location | Symptom |
|---|-----|----------|---------|
| 1 | Missing index on `orders.customer_id` | `schema.sql` | Full table scan on every order lookup → O(n) |
| 2 | N+1 query in `get_customer_orders()` | `app.py` | One DB query per order item instead of a JOIN |
| 3 | Connection not released in error path | `db.py` | Pool exhaustion under load; 503s after ~50 requests |
| 4 | Cache TTL set to 0 (bug from "latest commit") | `cache.py` | Every request is a cache miss; hides the real error rate from metrics |

Bug 4 is the most recent "commit" in `git_log.md` — it's a one-line change that
looks innocent ("fix cache invalidation on user update") but zeroes the TTL.

### Red Herrings

`app.log` contains noise from a co-located "auth-service" component:
- JWT expiry warnings (normal, not the problem)
- Occasional 401s from a test account (unrelated)
- A misleading `ConnectionResetError` from a client that disconnects early

An agent that fixates on the auth errors will waste turns and come up empty.

## Agent Architecture

```
IncidentCoordinator
│
├── [parallel, asyncio.gather]
│   ├── LogAnalystAgent
│   ├── DatabaseAgent
│   │   └── QueryProfilerAgent   (sub-agent, spawned by DatabaseAgent)
│   ├── CodeAuditAgent
│   ├── CacheAgent
│   └── HealthProbeAgent
│
├── [synthesis] IncidentCoordinator reads all 5 reports
│
├── HumanInput: approval gate
│
├── RemediationAgent
│
├── VerificationAgent  ← round 1: catches bug #3 was missed
│
├── RemediationAgent   ← round 2: fixes bug #3
│
├── VerificationAgent  ← round 2: green
│
└── PostMortemAgent
```

### IncidentCoordinator

System prompt instructs it to act as a senior SRE leading a P0 incident.
Dispatches the five investigators in parallel, waits for all reports, then
synthesizes a root cause analysis. It must rank findings by impact and identify
the causal chain before calling HumanInput.

Tools: none (it orchestrates via sub-agents).

### LogAnalystAgent

Investigates `service/logs/`. Tasks:
- Parse error rates by timestamp (errors/minute over the last hour)
- Identify the first error and what preceded it
- Distinguish service errors from auth-service noise
- Find the correlation between 503s and slow query log entries

Tools: `Bash` (grep, awk, sort), `FileSearch`.

Expected output: error timeline, identified noise sources, correlation finding.

### DatabaseAgent

Investigates the schema and query patterns. Tasks:
- Read `schema.sql` — identify missing indexes
- Run `EXPLAIN QUERY PLAN` via sqlite3 on the hot queries
- Check connection pool configuration in `db.py`
- Spawn `QueryProfilerAgent` for deep query analysis

Tools: `Bash` (sqlite3), `FileSearch`, `FileEdit` (read-only).
Sub-agent: `QueryProfilerAgent`.

### QueryProfilerAgent

Spawned by `DatabaseAgent`. Runs actual timed queries against the seeded DB,
compares execution plans with and without indexes, reports the speedup factor.

Tools: `Bash` (sqlite3, Python timing scripts).

### CodeAuditAgent

Reviews `app.py`, `db.py`, `cache.py`, and `git_log.md`. Tasks:
- Find N+1 query patterns
- Find error paths that don't release resources
- Read the fake git log and identify the most suspicious recent change
- Cross-reference the cache TTL with the git log timestamp

Tools: `FileSearch`, `Bash` (grep).

### CacheAgent

Investigates `cache.py`. Tasks:
- Find the TTL configuration
- Simulate cache behavior: show that every request is a miss
- Calculate the additional DB load caused by 0 TTL (compare to expected hit rate)
- Trace the TTL change back to a specific "commit"

Tools: `Bash` (Python), `FileSearch`.

### HealthProbeAgent

Runs the service directly and hits its endpoints. Tasks:
- Run the test suite, record pass/fail
- Hit the slow endpoint repeatedly, measure latency distribution
- Trigger pool exhaustion by making 60 concurrent requests, observe 503s
- Report which endpoints are affected and by how much

Tools: `Bash` (pytest, Python httpx or requests script).

### HumanInput (approval gate)

After synthesis, `IncidentCoordinator` calls `HumanInput` with:
- A summary of the four root causes
- The proposed fix plan (what will change in which file)
- Estimated risk level

The exercise auto-responds "approved" (same pattern as hitl_demo), but the
question is structured so a real operator could actually review it.

### RemediationAgent (round 1)

Applies fixes for bugs #1, #2, and #4. Bug #3 (connection leak) is
intentionally left out of the first plan — the coordinator's synthesis
underweights it because the HealthProbeAgent's pool exhaustion test was
inconclusive (50 requests didn't quite trigger it; the agent noted it as
"possible" rather than "confirmed").

Changes:
- `schema.sql`: add index on `orders.customer_id`
- `db.py`: re-seed the DB with the new schema
- `app.py`: rewrite `get_customer_orders()` to use a JOIN
- `cache.py`: restore the TTL to 300

Tools: `FileEdit`, `Bash`.

### VerificationAgent (round 1)

Runs the test suite. Finds:
- Most tests pass
- `test_concurrent_load` still fails intermittently (pool exhaustion: bug #3)

Returns a structured report: what passed, what failed, what the failure means.

### RemediationAgent (round 2)

Fixes bug #3 in `db.py`: wraps the error path in a `try/finally` to guarantee
connection release.

Tools: `FileEdit`.

### VerificationAgent (round 2)

Runs the full test suite. All green. Reports pass count and timing.

### PostMortemAgent

Writes a structured post-mortem to `exercises/incident_response/postmortem.md`:
- Incident timeline
- Root cause analysis (all four bugs, causal chain)
- What the red herrings were and why they were dismissed
- Fix summary
- What monitoring would have caught this earlier

Tools: none (synthesis and write).

## What This Exercises

| Nori capability | How it's stressed |
|---|---|
| Parallel sub-agents | 5 investigators running concurrently via `asyncio.gather` |
| Sub-agent spawning | `DatabaseAgent` spawns `QueryProfilerAgent` at runtime |
| Long context management | Coordinator synthesizes 5 full reports in one context |
| Iteration loops | Two remediation + verification rounds |
| HITL | Approval gate with structured, meaningful question |
| Real tool use | sqlite3, grep, pytest, Python — no mocks |
| Error recovery | Verification catches an incomplete fix; system self-corrects |
| Multi-file edits | Remediation touches 4 files in round 1 |
| Red herring resistance | Logs planted with noise; agents must filter it |

## Known Constraints

- `seed.sql` must be large enough (10k+ rows) that missing-index scans are
  measurably slow via sqlite3 timing, but small enough to generate quickly.
- `HealthProbeAgent`'s pool exhaustion test needs a connection pool limit low
  enough to trigger in < 100 requests (set pool size to 5 in `db.py`).
- The exercise should run end-to-end in under 10 minutes wall time.
- `postmortem.md` is the human-readable artifact; its quality is the ultimate
  measure of whether the exercise succeeded.
